# Anti-Pattern Library

Reusable anti-pattern examples organized by output type. Include the relevant section in any skill that produces that output type.

---

## File Outputs (Documents, Spreadsheets, Presentations)

### Never trust defaults
Libraries have defaults that may not match user expectations. Always set critical parameters explicitly.

**Example (docx-js page size):**
```
Wrong: Relying on docx-js default page size
Why:   docx-js defaults to A4, not US Letter — documents render with wrong margins on US printers
Right: Always set page size explicitly: width: 12240, height: 15840 (US Letter in DXA)
```

### Never use string hacks for structured content
When a library provides a structured API for something, use it — don't fake it with string manipulation.

**Example (docx bullet points):**
```
Wrong: new Paragraph({ children: [new TextRun("• Item")] })
Why:   Unicode bullets don't participate in list numbering, indentation, or style inheritance
Right: Use LevelFormat.BULLET with numbering config
```

**Example (docx line breaks):**
```
Wrong: new TextRun("Line 1\nLine 2")
Why:   \n doesn't create paragraphs in OOXML — it may render as a space or be ignored
Right: Use separate Paragraph elements for each line
```

### Always validate outputs
Never deliver a file without checking it opens correctly and meets format requirements.

**Example (docx validation):**
```
After creating the file, validate it:
  python scripts/office/validate.py doc.docx
If validation fails, unpack, fix the XML, and repack.
```

**Example (xlsx formula errors):**
```
Every Excel model MUST be delivered with ZERO formula errors:
  #REF!, #DIV/0!, #VALUE!, #N/A, #NAME?
Check with recalculation script before delivery.
```

### Never use percentage-based widths in documents
Cross-platform rendering breaks with relative sizing.

**Example (docx tables):**
```
Wrong: width: { size: 100, type: WidthType.PERCENTAGE }
Why:   Percentage-based widths break rendering in Google Docs, which many users open .docx files in
Right: width: { size: 9360, type: WidthType.DXA }
```

## Creative / Visual Outputs

### Never default to generic aesthetics
If the output could have been generated by any generic AI tool, the skill has failed.

**Blacklisted defaults:**
- Fonts: Inter, Roboto, Arial, system fonts (unless explicitly part of a minimalist design choice)
- Colors: Purple gradients on white backgrounds, generic blue (#007bff), Bootstrap defaults
- Layouts: Center-everything, uniform rounded corners, card grids with identical styling
- Spacing: Cookie-cutter 16px/24px/32px spacing with no intentional variation

**Instead:**
- Choose fonts with personality — distinctive display fonts paired with refined body fonts
- Choose colors that are specific to THIS topic — if swapping colors into a different project would still work, the choice isn't specific enough
- Choose layouts with visual tension — asymmetry, overlap, grid-breaking elements
- Choose spacing with intentional rhythm — not uniform padding everywhere

### Never skip the conceptual phase
Going straight to code produces convergent, forgettable output.

```
Wrong: "I'll create a modern, clean dashboard with a sidebar navigation..."
Why:   "Modern and clean" is not a design direction — it's the absence of one
Right: Choose a specific aesthetic (e.g., "brutalist data density" or "warm editorial dashboard")
       and let that direction inform every choice
```

### Never use the same aesthetic twice
If repeated outputs cluster around the same look, add explicit variety enforcement.

```
Wrong: Every generated landing page uses Space Grotesk + dark theme + gradient hero
Why:   Convergence signals the skill is anchoring on a single pattern instead of exploring
Right: Vary theme (light/dark), fonts, aesthetic direction, and layout structure across generations
```

## Code Outputs

### Never hardcode environment assumptions
Code should work across environments without modification.

```
Wrong: const path = '/Users/johndoe/Documents/project/'
Why:   Hardcoded paths break on any other machine
Right: Use relative paths, environment variables, or configuration files
```

### Never omit error handling
Every external call (file I/O, API, database) can fail.

```
Wrong: const data = fs.readFileSync('config.json')
Why:   If the file doesn't exist, this crashes with an unhelpful error
Right: Wrap in try/catch with actionable error messages
```

### Never leave placeholder/mock data in production code
If the skill was developed with test data, the instructions must specify removing it.

```
Wrong: const users = [{ name: "Test User", email: "test@test.com" }]
Why:   Mock data in production causes confusion and potentially exposes fake data to real users
Right: Connect to real data sources; if none available, show an empty state
```

## API / Integration Outputs

### Never assume auth persists forever
Tokens expire. Connections drop. The skill must handle re-authentication.

```
Wrong: Using a stored token without checking expiration
Why:   OAuth tokens typically expire after 1 hour; API keys can be rotated
Right: Check token validity before each request; handle 401/403 with re-auth flow
```

### Never swallow errors silently
Failed API calls should surface clearly, not disappear.

```
Wrong: try { await api.call() } catch (e) { /* ignore */ }
Why:   Silent failures leave users confused about why nothing happened
Right: Surface the error with context and suggested next steps
```

### Never expose credentials in outputs
API keys, tokens, and secrets must never appear in generated code, documents, or logs.

```
Wrong: console.log(`Calling API with key: ${apiKey}`)
Why:   Credentials in logs or output can be captured by downstream systems
Right: Log the action without the credential: console.log('Calling API...')
```

## Workflow Outputs

### Never ask too many questions at once
Multi-question dumps overwhelm users and reduce response quality.

```
Wrong: Asking 10 questions in a single message
Why:   Users skip questions, give shallow answers, or abandon the workflow
Right: Start with the 3-5 most important questions; follow up based on answers
```

### Never lose context between stages
Information gathered in Stage 1 must inform behavior in Stage 2.

```
Wrong: Asking the same question again in a later stage
Why:   Users lose confidence in the workflow and feel like their time is wasted
Right: Track what's been learned and reference it in later stages
```

### Never block on optional steps
If a step can be skipped, make that clear and easy.

```
Wrong: "You must complete all 5 sections before we can proceed"
Why:   Users with partial needs get stuck; completion rates drop
Right: "We can skip this section if it's not relevant — just let me know"
```

## How to Use This Library

When building a skill:

1. Identify the output type(s) the skill produces
2. Include the relevant anti-pattern sections in the skill's "Common Mistakes" section
3. Add domain-specific anti-patterns discovered during testing
4. Format as wrong/why/right for maximum clarity
